Learner brief for Week 5

Document for learners. Draft, not yet run with learners; the hours are provisional estimates.

What you will be able to do

By the end of this week you can do four things. You can list the ways your ship item could be wrong without you seeing it. You can lift one important rule in the ontology up to a gate, and prove that the gate can go red. You can set up a routine that runs on a schedule. And you can put your ship item in front of real users, then start measuring the “after” window.

The core question of the week is: how do you know it is right when you are not looking?

What to bring to Session 1

  • The ontology from Week 3 and the Given, When, Then acceptance criteria from Week 2.
  • The first version of your ship item and the files that describe the roles of the three-role team from Week 4.
  • Your AI work log: for each assignment, write what you gave, what the AI returned, and how you checked it.
  • A page to write on, in the tool you are comfortable with. The first twenty minutes use no AI.

Self-work this week

Estimate: 6 to 10 hours. This is the estimate of the independent grader, with no real measurement yet.

  1. Build the gate first: one rule in the ontology, one planted red case, one run that goes red, then fix that case so the run goes green. A gate is a check with a recorded result that can go red; the minimum form is a script with an exit code, or a fixed checklist run by a fresh grading session that writes a verdict file (no terminal needed). A gate must not go green when the number of cases checked or the number of PASS lines is 0.
  2. Set up one routine for a task you have already done twice. Write the run time and who triggers it into the schedule.md of Week 4 (add one row, do not open a second schedule). If your company tools do not allow automatic runs, you trigger it yourself at the time you wrote down.
  3. When the first version passes the gate, give it to 1 to 2 colleagues and record their feedback.
  4. At the end of the week, ship to real users and start measuring the “after” window the way you fixed it in Week 2.
  5. Submit the record of one red run and one green run, together with the two lists “observed” and “assumption”, 24 hours before Session 2. Two graders read them at home.
  6. Read new-content-operations-control-risk-and-metrics.md (same folder) and do its four exercises on your ship item, about 50 minutes: one preventive control and one detective control for three tasks; three metrics for the routine; a risk table for the three tasks; one escaped defect turned into a check.

How you are graded

Each submission is graded by two other learners in Session 2, paired by rotation; the facilitator announces the pairing table. They count evidence only: a record with a real command and exit code (or a verdict file), a screenshot, or a live run in the class. A spoken account does not count.

The grader picks one red case at home, and you run the gate with that case in front of the class in 4 minutes. The gate must go red in the right place. They also question you for 3 minutes with Socratic questions about your decisions.

They answer four questions: is there a record, a screenshot or a live run; does it connect to the number of the ship item; can you answer the question about the decision; does your submission separate what is certain from assumption. The result is one of three: pass, needs revision, not enough evidence; if the two graders differ, the stricter result stands, and the facilitator does not decide. If it needs revision, you fix it and submit again.

Every submission opens with the list of what was observed that the submission relies on, kept apart from what is only assumption.

Permitted AI level

  • The first twenty minutes of Session 1 and the redo on paper in the defence: no AI.
  • Choosing the rule, deciding what the gate checks: the AI gives a draft for you to challenge; you point out what is wrong, fix it and defend the choice.
  • Writing the script for the gate and the routine: you may hand all of it to the AI; you run it yourself, check the result yourself and keep the log.

Any AI tool is allowed. Use only the tools your company permits, open several sessions if needed, and do not send data outside.

If you are stuck

  • The gate never goes red: plant a defect in the input and run again. If it is still green, check whether it is checking 0 cases.
  • No rule in the ontology yet: use one acceptance criterion from Week 2.
  • Your company stops you from releasing on time: tell the facilitator early; you can ship an internal tool or process that colleagues really use.
  • No colleague to try it: ask a person sitting next to you to use the first version and you record what they do.
  • Still stuck after two tries: stop, write down what you did and what the result was, then bring it to the unblocking support in Session 2.

Six types of Socratic question

In the break-down part, the facilitator steps in with at least three types of Socratic question.

TypeSample question
Probe assumptions“What are you believing when you say ‘the test is green’? Who wrote that test?”
Probe reasons and evidence“Have you ever seen that very test go red? What makes you sure it can go red?”
Ask about consequences“If this gate is green while the ship item is wrong, which user suffers first and how do they find out?”
Clarify“When you say ‘done’, which exact command was run, and which result did you see?”
Look for another viewpoint“A real user, a colleague who has not seen this work, and an independent grader agent: which defect would they see that you missed?”
Question the question itself“Is ‘know it is right’ the right question, or is the real question ‘know where it is wrong’?”

The model in plain words

  1. A gate must be proven to be able to go red. A gate that has never gone red knows nothing about whether it does its job.
  2. Check along a ladder from cheap to expensive: syntax checks and one-line commands first, live runs next, an independent grader last.
  3. A command that has finished is not the same as done. Exit code 0 only says the program did not crash, not that it checked what needed checking. For a checklist-style gate, the “exit code” corresponds to a verdict file with a real PASS line.
  4. A task done twice becomes a skill or a routine.
  5. Each escaped defect must become an automatic check, with one planted-fail test; and that check must be attached to the right step where results are sent out, otherwise it is only documentation.

The six-level ladder of a rule

The higher a rule climbs, the harder it is to get wrong. This week you lift one rule to level five.

LevelWhat it is
1Words or a comment
2A ruling with a date and a scope
3A rule in the list the agent reads by default
4A component API that does not let a wrong value pass
5A gate that goes red at build time
6An independent grader with the feedback recorded

A gate in its minimum form

A gate in its minimum form is a check with a recorded result that can go red. There are two kinds, and you choose one:

  1. A script with an exit code, run with one command in your own terminal.
  2. A fixed checklist run by a fresh grading session and written into a verdict file (use the four words PASS, FAIL, NOT_VERIFIED, NOT_APPLICABLE as in the Week 4 kit). This kind is for people without a terminal.

A gate counts as green only when the number of cases checked or the number of PASS lines is greater than 0; a verdict that has only NOT_APPLICABLE is not green.

The routine lives in the schedule.md of Week 4: add one row or turn one Week 4 run into a repeating schedule; do not open a second schedule file.

Operations and control: learning material and exercises

Status: draft, not yet run with learners. This is new content because the owner has no material on risk management or operating metrics in the business-management sense. The management sources below were found by web search in the writing session; most results are secondary sources, so wherever the original text could not be opened it is marked “original source not verified”.

Each concept has a definition, how to apply it to agents in the job you do now, an example, common mistakes and a short exercise. “The job you do now” means you have a manager and colleagues; nobody here is starting a company.

1. Internal control

Definition

Internal control is the set of activities, policies and procedures that help an organisation reach its goals without letting errors or fraud get through. The COSO framework (2013) splits it into five components, and “control activities” are the actions set out in policies and procedures so that management’s directions are carried out. There are two kinds of activity: preventive (stop errors before they happen, for example separating the maker from the approver, approval in advance) and detective (find errors that have already happened, for example reconciliation, reading exception reports).

Source: COSO, Internal Control, Integrated Framework, 2013, via the summary at iasplus.com and the McGill internal audit page mcgill.ca. Checked on 2026-11-13: the link COSO Q&A is the COSO Q&A on this framework (May 2013), not the text of the framework. The Q&A confirms the five components (control environment, risk assessment, control activities, information and communication, monitoring activities), three groups of objectives (operations, reporting, compliance) and seventeen principles; it ties control activities to building and deploying policies and procedures. It does not mention the two kinds, preventive and detective; those two kinds still come only from secondary sources. The full text of the framework has not been read.

Apply to agents in the job

A gate is an automatic control activity, detective or preventive depending on where you place it. Separating the agent that makes from the agent that grades is separation of duties (segregation of duties). The who-approves-what table from Week 4 is a policy on who may do what. If you have a manager, one more point is needed: a task that your manager must know about or approve before shipping is a company control, and an agent does not replace it.

The owner’s example

Three process gates: a quality threshold (each criterion at least 8, the total at least 9 for the part the customer sees), the grader is never the maker, and a hardening loop that turns each escaped defect into an automatic check with a planted-fail test. Source: the owner’s OPC article, the process section. The owner does not call them “internal control”; attaching that label is done by this document.

Common mistakes

Having only detective controls after shipping, and no preventive control before tasks that cannot be undone. Or having a correct control that is not attached to the process, so it runs when someone remembers to call it (the OPC article itself records this mistake and how to attach it again).

Exercise: internal control

10 minutes. Choose three tasks in your ship item. For each task, write one preventive control and one detective control, then underline whichever one does not exist yet.

2. Operating metrics

Definition

Operating metrics measure how well the internal process runs, unlike financial metrics, which measure the final result. According to search results about the article by Kaplan and Norton (1992), the two authors propose looking at a business from four perspectives: customer, internal process, innovation and learning, financial. Operating metrics sit in the “internal process” perspective. A way of picturing it from the writer of this document (not the words of the two authors): a set of metrics is like a dashboard, and each gauge answers a different question.

Source: Robert S. Kaplan and David P. Norton, “The Balanced Scorecard: Measures That Drive Performance”, Harvard Business Review, January to February 1992, pages 71 to 79. Copy found: archive.org. Checked on 2026-11-13: the Harvard Business Review page confirms the article title, the two authors and the January to February 1992 issue. The body of the article is behind a paywall, so the content of the four perspectives above could still not be checked against the original article. The copy on archive.org is not the publisher’s version and has not been opened.

Apply to agents in the job

Each three-role team and each routine should have three kinds of metric: quality (the share of runs that pass the gate the first time), speed (the time from receiving the task to having a result that has passed the gate), cost (the number of runs, tokens or human hours spent per unit of output). This is how to connect to the number from Week 4: the agent running cost per unit recorded there becomes an operating metric.

The owner’s example

The owner has not called anything an “operating metric”, but there are measurements that can be read in this sense: in the article about the PO and the AI design agent, all 34 comment threads of 29/10 were answered, and the time from opening a thread to the first reply has a median of 31 minutes (range about 3 to 114 minutes); the owner’s PO and AI design agent article. This is a self-reported figure from the article, not re-run; and it is a speed metric, not yet connected to revenue. A second example: the ratio of 7 out of 11 issues below the threshold in release v0.7.5 is a quality metric for one release (the owner’s OPC article).

Worked example step by step

Constructed example, numbers set by the writer, not the owner’s. Routine: every Tuesday the three-role team triages 20 bug reports (Week 4). One unit of output is one batch of 20 triaged bug reports.

  1. Name the unit: reuse the unit you chose in Week 2; in this example that unit is one batch. Every metric below is counted per that unit.
  2. Quality: the share of batches that pass the gate on the first run. How to measure: count the NNN-verdict.md files (not re-runs) that have the line VERDICT: PASS, and divide by the number of batches. Suppose 4 batches, 3 pass at once: 75%.
  3. Speed: the minutes from writing NNN-task.md to having a PASS verdict. How to measure: the times written in schedule.md and cost-log.md. Suppose the median is 35 minutes.
  4. Cost: your minutes plus the agent running cost (money or tokens) per batch, taken from cost-log.md. If a number is missing, write “not measured”.
  5. Who sees it change: if 75% drops to 50%, you see it next week, and the person who reads the triage (a developer colleague) sees it in the number of defects missed.
  6. How the metric connects to the outcome number of Week 2: not linked yet; this is an early signal of the machine, not evidence of the outcome. Trap to avoid: counting how many times the routine ran instead of how many batches passed the gate.

Common mistakes

Measuring what is easy to measure instead of what decides the conclusion, for example counting how many times the routine ran instead of the rate of correct runs. Or measuring an operating metric and then using it as evidence of a business result. The owner’s growth article names a nearly identical mistake: grade with the wrong ruler and the conclusion is wrong (the owner’s 8-day growth article, the measurement section).

15 minutes. For your routine, write one quality metric, one speed metric and one cost metric using the six steps above. For each metric write: how it is measured, by which command or record, and who will see it change.

3. Risk management for tasks that cannot be undone

Definition

Risk management is the process of identifying, analysing, evaluating and then treating risk. According to ISO 31000, the level of a risk considers likelihood and consequence together, and the treatment is based on that level. The four treatments below are a common shorthand in secondary material, not a list quoted from the ISO 31000 text: avoid, reduce (lower the likelihood or the consequence), transfer or share, retain. After treatment there is residual risk, and its effect needs to be monitored over time.

Source: ISO 31000:2018, Risk management, Guidelines (standard page); secondary summaries read in this session: ecampusontario.pressbooks.pub and ideagen.com. Original source not verified: the ISO standard text cannot be read for free and was not opened; only the summaries were used. On 2026-11-13 the standard page on iso.org was tried again: it still returns code 403.

Apply to agents in the job

Since Week 4 you have asked, for each task: if it is done wrong, can it be undone? The risk framework adds two axes: likelihood of error and consequence. A task that can be undone and has a small consequence is run by the agent on its own. A task that cannot be undone (sending a message, shipping to users, deleting, spending money) has its risk reduced by adding an approver, a planted red case, or a trial on a copy first. Shipping to real users at the end of Week 5 is exactly such a task.

The owner’s example

The owner has a classification of tasks that can be undone and those that cannot; apart from reading the spec at the gates, the owner approves by hand only six tasks that cannot be undone (merge, tag or publish, posting, sending a message, deleting, spending money); the owner’s OPC article, the section on what I approve. The owner has no example yet for a likelihood-times-consequence framework or a risk register.

Constructed example (not the owner’s). A QA learner plans to let the agent close tickets by itself when the tests are green. Likelihood of error: medium, because the tests may not cover everything. Consequence: a ticket closed by mistake, the defect reaches the user, hard to undo because nobody reopens it. Treatment: reduce the consequence by having the agent only propose closing and a person approve by hand; retain the residual risk of wrongly closing one small ticket.

Common mistakes

Rating the likelihood of error by feeling (“the agent is good now”) instead of by the record of runs. Or treating a risk that has been reduced as gone, and forgetting the residual risk.

Exercise: risk table

15 minutes. Build a table of three rows for the three tasks of the ship item: likelihood of error (low, medium, high) with evidence, consequence if wrong, can it be undone or not, treatment among the four, residual risk. For a row that cannot be undone, write who approves.

4. Continuous improvement

Definition

Continuous improvement is the repeating of one small cycle: plan a change, try it at small scale, look at the result and take the lesson, then act on the lesson. The cycle is called Plan, Do, Check, Act (or Plan, Do, Study, Act), linked to Shewhart and Deming. If the trial fails, go back to the planning step with a different plan, and the cycle repeats without stopping.

Source: American Society for Quality, “PDCA cycle”, asq.org. Original source not verified: this page returned a 403 error when opened, so the summary comes from ASQ search results and the whole page has not been read. Tried again on 2026-11-13: the ASQ page and the page of the Deming Institute (deming.org) both returned code 403.

Apply to agents in the job

Each defect that gets through the gate is one loop: put in a new check (Plan), install it in the process and try it with a planted-fail case (Do), run the gate again to see whether the check catches it (Check), keep or fix that check (Act). What to avoid is skipping the Check step: a check that is written and that nobody has seen go red is not yet an improvement.

The owner’s example

The six-step self-evolution loop: the owner’s feedback becomes a one or two line lesson, scan for conflict with old rules, write it as an automatic check with a planted-fail test, another bot validates, then attach the check to the right step where results are sent out; the owner’s OPC article, the self-evolution section. The owner does not call it PDCA. A concrete example in the article: on 29/10 a LinkedIn post was criticised, the Maintainer turned all the feedback into 10 checks with sample files that are deliberately wrong, then switched one check off to see whether the test reports the escape.

Common mistakes

Fixing the defect without changing the process, so the defect comes back. Or adding checks without limit until the process is heavy; each new check should be able to answer “which defect does it catch”.

Exercise: continuous improvement

10 minutes. Take one defect that got through your ship item or your gate this week (if there is none, plant a defect). Write four lines Plan, Do, Check, Act for that defect, where the Check line states the command you run to see the check go red.

How the four concepts connect

Internal control puts the gate in the right place. Risk management decides which gate must have an approver and not only run automatically. Operating metrics tell you whether the gate and the routine run well. Continuous improvement turns each escaped defect into a new check. If you have a manager, all four sit inside the company’s control framework: where the company already has an approval process, that process wins over the agent.
