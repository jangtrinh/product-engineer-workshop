Learner brief for Week 4

Week 4: One-person company (OPC), the version for you. Status: draft, not yet run with learners. The hours are provisional.

What you will be able to do

By the end of the week you can run a three-role team (coordinator, maker, grader) to build the rest of your ship item. Specifically:

  • Sort each task of the ship item into three tiers: the agent runs on its own, you approve by hand, or someone with higher authority than you approves.
  • Turn the working rules you wrote in Week 1 into rules of the one-person company: each rule is attached to a role, to a grading criterion or to a row of the who-approves-what table.
  • Write the role file for each of the three roles. Each file has one job and one prohibition.
  • Make the grader agent catch a planted defect, live in class.
  • Record the real agent running cost and work out the cost per unit (the unit you chose in Week 2): your minutes, money or tokens, or “not measured” when there is no number yet.

The idea of this week: you run the agent team like a one-person company, but within the authority the company has given you. You have a manager and colleagues, so some things you may not approve yourself.

What to bring to Session 1

  • The list of tasks still left in the ship item.
  • The Week 2 spec (the numbered tasks and acceptance criteria).
  • The working rules you wrote in Week 1.
  • The ontology and the first skill from Week 3.
  • Your company’s rules on AI tools and data.
  • Something to write on, because the first part of the session uses no AI. Use the tool you are comfortable with, or paper and a pen.
  • The AI tool you chose, able to open three separate chats.

The self-work list of the week is in part C of this page. The kit (version 0.4) is on its own page: Agent-team kit. The additional reading is in part D.

How you are graded

Two other learners grade you in Session 2, paired by rotation; the facilitator announces the pairing table. They read the package you handed in at home, choose exactly one acceptance criterion in your spec and message you before the session. You prepare a result changed so that it violates exactly that criterion, then in class you run a new grading session live (4 minutes).

You pass when both of these are true:

  1. The grader agent catches the defect and states clearly which criterion it is.
  2. No irreversible task is given to an agent.

The graders look at the record, the screenshots and the live run. A spoken account does not count. The outcome is one of three: pass, needs revision, not enough evidence; if the two graders differ, the stricter outcome stands. The facilitator does not decide the outcome. If it needs revision, you fix it and hand it in again. You do not grade your own work.

Your submission starts with two short lists: what you observed, and what is only an assumption. In Session 2 you also have a 5-minute defence: point to one task that you keep for a person, one task that you give to an agent, and the evidence you need to see before you trust it.

If you are stuck

  • The company allows only one AI tool: open three new chats in that tool, one chat per role.
  • The company forbids opening several sessions or forbids putting data into AI: message the facilitator before Session 1 to find a way together; do not bypass the company rule on your own. Two sessions (maker and grader) is the minimum; never let one chat hold two roles, even if you separate them by time.
  • You do not know which tasks are reversible: put them in a higher tier and ask your manager.
  • The grader agent reports pass every time: add a specific check to its role file, do not change the criterion to make it easier to pass. The guidance is in section 8 of the kit.
  • The tool does not report tokens: write “not reported”.
  • Still stuck: message the facilitator with the team/ folder and one line saying at which step of the kit you stopped.
  • The maker’s chat writes the result of a command that it did not run: you run the command yourself, then add the section “Human-run evidence” to the result file.

The model in plain words

A one-person company is one person plus a team of agents with rules written on paper. Each agent has exactly one job and one prohibition. A reversible task is run by the agent on its own; an irreversible task is approved by a person by hand. The maker and the grader are two different sessions. The whole team reads the same ontology. In a real company there is one more idea: accountability goes up the chain, so an agent never bears accountability and an irreversible task may have to go through the manager.

Closing question

The grader agent returns a PASS verdict for the version the maker agent wrote. This version will be sent to a whole group of colleagues. What is the most correct next step?

  • A. Send it at once, because an independent grader has already checked it.
  • B. Ask the maker agent whether it is sure the version it wrote is right.
  • C. Open the product, check yourself that each PASS line has evidence, then send it by hand yourself.
  • D. Let the grader agent run again until three runs give the same PASS, then send it.
Show the model answer

The correct answer is C. A treats the agent’s verdict as approval, so no person has approved the irreversible task. B lets the maker confirm itself. D treats repetition as independence: the same blind spot repeated three times adds no information.

Learning material: OPC for an employee with a manager

Status: draft, not yet run with learners. This is the part of the syllabus marked “Must be written new” for Week 4: OPC for an employee with a manager, and the split of authority between human and agent in an organisation with a chain of command. The owner’s model is the owner’s own company, so every example here for the case of an employee is a constructed example, clearly marked.

Reference codes: the concept name comes first; an abbreviation such as RACI is only a secondary name after the full name.

One model, two situations

The owner defines OPC in five lines. The main idea is that one person keeps the direction, the taste and the final approval, while the rest of the work is done by bots, rules written in files and automatic machine checks (source: the owner’s OPC article, section “OPC của mình nghĩa là gì” [What OPC means for me]). In that article the owner names themself System Architect and the person who approves the irreversible tasks. The article does not say whether the owner has a manager or colleagues; because this is the owner’s own company, the writer infers that no superior approves in the owner’s place (inference; no sentence in the article confirms it).

The learner differs from the owner in exactly one point: their authority has limits, and someone else sets those limits. The four concepts below answer the same question, “with the authority I really have, what can I give to the agent and who is accountable?”, and then the fifth concept puts them together.

1. OPC as an operating model for a person with a manager

Definition

The learner runs a small team of agents like a one-person company, but this company sits inside the authority that the real company and the manager have given them. The learner does not found a company and does not become a manager; they remain a builder (course contract, sections 5 and 10).

Why it matters for a product engineer

An employee may not widen their own authority. If the agent team does a task beyond the authority the learner has, the consequences fall on the learner and the manager, not on the agent.

Apply to the work at hand

What stays the same from the owner’s model: each role has one job and one prohibition, a reversible task is run by the agent on its own, an irreversible task is approved by a person by hand, and a task decided once is not asked again. What must change: “the person who approves by hand” is no longer always the learner. Some tasks the learner can approve, others must go through the manager or through the company’s process.

The owner’s example

A task that can be redone is run by the bot on its own, including writing a spec, pushing a branch, opening a PR. Apart from looking at the spec at the gates, the owner approves by hand only six irreversible things: merge, tag and publish, post, send a message, delete, spend money (same OPC article, section “Mình duyệt gì, và không duyệt gì” [What I approve and what I do not]; the sentence about the spec at the gates is in section “Từ ý tưởng tới ship” [From idea to ship]). The owner has no example yet for this concept in a person with a manager.

Show the constructed example

Constructed example. A QA engineer in a retail company ships an internal tool that classifies bug reports automatically. Of the owner’s six things, she can approve two herself (sending a message in her own QA team, merging into the code repository of her own tool). The other four are outside her authority: closing tickets in the shared system, changing the shared system configuration, sending a message to a customer, spending money. For those four, the agent team must not touch them, and the approver is her manager.

Common mistake

Copying the owner’s six tasks as if they were your own list. Your own list must come from the real consequences in your own company.

Exercise (10 minutes)

List the last five tasks of the ship item. For each task, write: who in the company is affected if it is wrong, and do I have the authority to decide it myself.

Exercise 1: last five tasks

2. Delegation and accountability

Definition

Delegation is when a manager hands a part of their authority and a part of their responsibility to a person at a lower level, usually by assigning tasks and sharing decisions. Accountability is the duty to answer for the result; it goes upward. The OpenStax textbook Introduction to Business describes exactly this: authority and responsibility go down the chain of command, while accountability goes up when the higher level answers for the actions of the lower level (Gitman et al., 2018; see Sources). The same textbook defines accountability as “responsibility for outcomes”, that is, responsibility for the results.

Why it matters

The agent does not stand in the company’s chain of command. Nobody asks the agent why a release was faulty; people ask the learner, and then ask the learner’s manager. So giving a task to an agent can transfer only the doing, not the duty to answer.

Apply to the agent

This rule can be read as a chain: the company gives to the manager, the manager gives to the learner, the learner gives to the agent. A consequence that the OpenStax text does not state directly (this is the writer’s inference): at each link, the receiver cannot take more authority than the giver has. The learner cannot give the agent authority that the learner does not have.

The owner’s example

The owner talks to J, J coordinates, and the owner does not assign tasks to each bot (same OPC article, section “Đội hình” [Line-up]). In the PO and AI design agent article, the PO keeps the decisions that can be seen, and the agent keeps the part that can be checked by tests and screenshots (section “Đội hình” [Line-up]). In both articles, the person at the end of the chain is still the one who does the merge or gives the approval.

Show the constructed example

Constructed example. The same QA engineer as above. The maker agent wrongly labels a serious bug “no fix needed” and the dev team ignores it. The manager asks her, not the agent. If in the team’s document the “accountable” column of the bug classification task carries the agent’s name, that document is wrong from the start.

Common mistake

Writing the agent in the accountable column, or thinking that “the agent does it, the agent grades it” is enough delegation.

Exercise (10 minutes)

Choose one task already given to an agent. Write one sentence: if this task is wrong, who is asked first, and who is asked second.

Exercise 2: who is asked first

3. Separation of duties (maker apart from grader)

Definition

Two duties that can hide each other’s mistakes are not held by the same party. In the NIST SP 800-53 Rev. 5 security control catalogue, control AC-5 requires the organisation to identify and record the duties of individuals that need to be separated, and then to define system access authorisations that support the separation. The explanation of the control says that separating duties aims to reduce the chance of abuse of the authority that was granted. The control text was checked on 2026-11-13 against the OSCAL version published by NIST (see Sources).

Why it matters

If the maker and the grader are one, nobody sees the mistake. With agents this mistake happens very easily, because “grading” is just opening one more chat window.

Apply to the agent

Two conditions, in order: the grader must be a separate session with a separate role file, and the grader cannot read the maker’s reasoning, only the result and the acceptance criteria. The second condition is the writer’s inference, not yet verified with learners.

The owner’s example

The owner’s Principles set three rules: the grader is never the maker; QA grades and does not fix what it is checking; a bot that writes rules may not approve its own rules (OPC article, sections “Principles” and “Từ ý tưởng tới ship” [From idea to ship]). A real incident the owner tells: a CLI reported done without having written any file (OPC article, section “Vì sao mình dùng Grok Bot” [Why I use Grok Bot]). A report of “done” is not evidence by itself.

Show the constructed example

Constructed example. A learner opens one window, pastes the maker role, then in that same window types “now grade the work just done”. The grading window has already read all of its own arguments, so it grades exactly the way it already thought.

Common mistake

Renaming the role inside the same session and treating it as separated. A lighter mistake: using the same role file for both sessions.

Exercise (10 minutes)

For your three-role team, fill in a three-column table: role, which files it reads, which file it writes to. Cross out every cell in which the grader can read what the maker thought.

Exercise 3: roles, files read and written

4. Responsibility matrix: responsibility assignment matrix (RACI)

Definition

The table has the tasks down the side and the roles across the top. Each cell holds one of four letters: R (Responsible, the one who does), A (Accountable, the one who approves and is finally accountable), C (Consulted, the one who is asked for an opinion), I (Informed, the one who is told). Some project-management theories require each task to have exactly one person in the A column; not every source treats that as a general rule (Wikipedia, section Responsibility assignment matrix, read in this session).

Mapping to the kit’s table

The kit’s “who approves what” table (version 0.4) splits the letter A into two columns: “Approves” (who allows the task to run or to go outside) and “Accountable” (who is asked if it is wrong); R is the column “Who does it”, and C and I are merged in “Who needs to know”. For the learner these two columns are often the same person, but not always: a Tier 3 task is approved by the manager, yet the learner is still the one asked first before the manager is asked.

Why it matters

In an organisation with a manager and colleagues, the question “who approves” is not clear by itself. The table makes the person who does the work name each person, including the manager.

Apply to the agent

Add two rule rows for the agent column: the agent can be R (does), never A. And for every irreversible task, A must be a named person, not a role.

The owner’s example

The owner has no example yet for RACI. The nearest is the four-role table of PO, Reviewer, Coordinating agent, Executing agent with the two columns “What it does” and “What it does not do” (PO and AI design agent article). That is a role table, not a RACI table; it lacks a column for the person who is informed.

Show the constructed example

Constructed example (a QA engineer in a retail company, the bug-classification tool):

TaskMaker agentGrader agentLearnerManagerDev colleague
Draft the classification for 20 bug reportsRAI
Grade the classification against the criteriaRA
Give the classification to the dev team to readR, AII
Close tickets in the shared systemRAC

The last task is irreversible and outside the learner’s authority, so A is the manager and the agent team has no letter in that row.

Common mistake

Two people in the A column for one task, or an empty A column because “everyone knows”.

Exercise (15 minutes)

Build the table for your ship item, at most eight rows. Check: each row has exactly one A, A is always a person, no agent is A.

5. Authority split between human and agent in an organisation with levels

Definition

Three tiers of authority for each task, matching the “Tier” column of the kit: Tier 1, the agent runs on its own; Tier 2, the learner approves by hand; Tier 3, someone with higher authority (the manager, a control function, the company process) approves. A task is put in a tier by two questions: can a wrong result be taken back, and does the learner have enough authority in the company to decide it alone.

Why it matters

This is where the owner’s model has to change the most. The owner has two tiers, bot and owner. The learner has three tiers, and the third tier is outside their control.

Apply to the work at hand

Read three sources before putting tasks into tiers: the company’s rules on AI tools and data (the learner asked about them in Week 0), the learner’s real authority in the system, and the agreement with the manager. When not sure, put the task in a higher tier.

The owner’s example

The owner has no example yet for this concept. The nearest is the four levels of rules company, project, role, task, and the rule that a lower level may only tighten, never loosen, the rules of the level above (OPC article, section “Principles v1.0”). That rule applies to the learner as it is: the rules of the agent team must not loosen the company’s rules.

Show the constructed example

Constructed example. The same QA engineer’s ship item:

  • Agent runs on its own: draft the classification, grade the classification, write the result file.
  • Learner approves: send the classification to her own small group.
  • Higher authority approves: close tickets, change the configuration, put customer data into the tool.

If the company rules allow only one AI tool, all three roles run in three sessions of that tool.

Common mistake

Tiering tasks by the feeling “the agent can probably do it” instead of by the consequence. Also common: ignoring data, because data that goes through an outside tool is a kind of irreversible task.

Exercise (15 minutes)

Sort ten tasks of the ship item into the three tiers and write one sentence of reason for each. Pick out the tasks you are not sure about and say who could answer.
