Minimal agent-team kit (three roles, independent of any tool)

Status: draft version 0.4, not yet run with learners. Version 0.1 was dry-run once on 2026-11-13 with a Claude model, on a ship item built as text; version 0.2 fixed the eight gaps that attempt found and three points from the independent grader. Version 0.3 fixed five more points from the re-grading run: the re-run of a task whose product must be run, the "not sure" row, the meaning of the approval line at Tier 1, the file name of the planted-defect test, and the cost unit. Version 0.3 was re-run on 2026-11-13, also with a Claude model, on a ship item that is code (a Python script): two tasks, ten role sessions, the first PASS verdict, and the planted defect was caught on both models tried. Version 0.4 fixed on paper the eight points that run found: when the whole ship item is done, a follow-on task must carry the old product, who writes the next task, not asking the maker to run commands, the file name when pasting the planted-defect version, re-running the planted-defect version, the verdict line for a criterion outside the task, and the source of the human-run evidence. An Opus model read version 0.4 right after that: five points were closed, three were only partly closed, and there were three more places where learners get stuck (materials only the runner uses, the meaning of NOT_APPLICABLE in section 8, the loop that writes the next task). That run added one sentence to step 3 and two sentences to step 10 of section 7; those sentences have not been read by anyone else. No version has been tried with a tool other than Claude or with a real person passing the files. It works with any AI tool that has a chat window. Each role is its own session (chat). The roles do not talk to each other: they read and write files, and you are the person who passes the files. You are also the person who triggers each scheduled run in section 5.

Two conventions used throughout the kit:

  • Save to file means you copy the agent's whole answer into the file with the matching name, changing no word.
  • Paste the file means you paste the whole content of the file into the chat window, with one line above it giving the file name.

1. Folder

Create a team/ folder with the following structure. This folder holds only information you are allowed to put into your AI tool.

team/
  shared/ontology.md              copy from Week 3
  shared/spec.md                  copy the Week 2 spec as it is: the numbered tasks and acceptance criteria
  shared/working-rules.md         the working rules you wrote in Week 1
  shared/who-approves-what.md     the table in section 4
  shared/skill-<name>.md           the skill you packaged in Week 3 (if the task at hand is of that kind)
  roles/coordinator.md  roles/maker.md  roles/grader.md
  inputs/                         materials for each run (notes, figures, code snippets) that the task will use
  handoff/001-task.md  001-result.md  001-verdict.md
  schedule.md   cost-log.md

A re-run of the same task keeps the old number and adds a suffix: 001-result-r2.md, 001-verdict-r2.md. A new task raises the number: 002-....

If the company allows only one AI tool, open three new chats in that same tool. Each chat is one role. Never use one chat for two roles.

2. Role files (paste verbatim as the first message of the session)

Edit the parts inside <...>; keep the "One job" and "Never" lines as one sentence each.

roles/coordinator.md

Role: Coordinator.
One job: Split the ship item <ship item name> into small tasks and write each task to a task file in exactly the format pasted with it.
Never: Give an agent a task for which the column "Reversible if wrong?" of the table shared/who-approves-what.md says "no" or "not sure", or write the word APPROVED yourself.
Reads: shared/spec.md, shared/ontology.md, shared/working-rules.md, shared/who-approves-what.md, the materials of this run, the verdict files, and the product of the previous task that got PASS, if it is pasted.
Writes: handoff/NNN-task.md. Copy each acceptance criterion that applies word for word, and the materials the maker needs word for word, into the task, because the maker reads only the task file.
Use exactly the terms in the ontology. If you meet a word that is not in the ontology, or a task that matches no row of the table, write "not linked yet", do not guess.
A task that fixes or continues an existing product: copy that product word for word into the Materials section, and put back into the task the criteria that product has already passed. If that product is not pasted, the last line is NEEDS_CONTEXT.
Do not ask the maker to run commands or to test: the maker cannot run commands; running is the job of the person who passes the files.
Materials that only the runner uses (for example a data file too large to paste): do not copy the content into the task; write the file name on the line "Materials only the runner uses".
If materials are missing, so that you cannot write a task the maker can do straight away, the last line is NEEDS_CONTEXT, not DONE.
Last line of every answer: STATUS: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT

roles/maker.md

Role: Maker.
One job: Do exactly one task written in the task file and write the result to the result file.
Never: Grade yourself, declare your own task passed, or write the output of a command you did not run.
Reads: shared/ontology.md, shared/skill-<name>.md if pasted, exactly one file handoff/NNN-task.md, and the verdict file if this is a re-run.
Writes: handoff/NNN-result.md with five sections: Product; Steps taken; Evidence; Points for the approver to check; Not done.
Evidence section: if you cannot run commands, write "No command was run" and state the commands the person needs to run.
Work outside the task file goes in the section "Not done", do not do it yourself.
Last line: STATUS: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT

roles/grader.md

Role: Grader.
One job: Check the result file against each acceptance criterion and write the verdict.
Never: Change the product, or read the maker's reasoning outside the result file.
Reads: shared/spec.md, shared/ontology.md, handoff/NNN-task.md, handoff/NNN-result.md.
Writes: handoff/NNN-verdict.md. One line for each criterion in shared/spec.md, including criteria that are not in the task: the criterion number, one of four words, the evidence quoted from the result.
  PASS: evidence can be quoted from the result.
  FAIL: the violating line can be quoted.
  NOT_VERIFIED: the criterion applies but the result and the materials are not enough to conclude. State clearly what is missing.
  NOT_APPLICABLE: the Given part of the criterion does not occur with the materials of this run, or the criterion does not belong to this task. State clearly why.
The section "Human-run evidence" in the result, if present, was added by the person who passes the files after running the product themselves: it is the person's observation, not the maker's word. You may use this section as evidence; what you cannot check about its source goes in the section "What I could not check".
After the criterion lines, write the section "What I could not check".
Last line: VERDICT: FAIL if there is a FAIL line; otherwise NOT_VERIFIED if there is a NOT_VERIFIED line or no PASS line at all; otherwise PASS.

3. Hand-off file format

Each run has three files, numbered the same.

NNN-task.md (the coordinator writes it; this is the block you paste to the coordinator, together with its role file, at step 3):

Task: <one sentence>
Acceptance criteria that apply: <the number and the exact words of each criterion>
Materials: <the exact content that may be used>
Materials only the runner uses: <file name, if any; do not paste the content>
Row in the who-approves-what table: <copy the task name from the first column>
Tier: 1 | 2 | 3
Approver: <leave blank; the person fills it in>
APPROVED by: <leave blank; the person fills it in>
STATUS: ...

NNN-result.md (the maker writes it): the five sections named in the role file, then the STATUS line. If the product must be run to know whether it is right, you add a sixth section Human-run evidence (step 6).

NNN-verdict.md (the grader writes it): the criterion lines; What I could not check; the VERDICT line.

Rule: a file with no STATUS or VERDICT line at the end counts as not finished. An agent's STATUS "done" is not yet evidence; evidence is something you can open and see.

A task with VERDICT: PASS is not yet the whole ship item done. The ship item is done when every criterion in spec.md has a PASS line in the verdict of the final version of the product. A criterion that so far has only a NOT_APPLICABLE line is a criterion that has not been checked. A criterion that is NOT_APPLICABLE because the materials do not yet have that case: add materials so that the Given part occurs, then give it as a new task. In the dry run of 2026-11-13 with code, the first task got PASS when only one of five criteria had been checked.

4. The who-approves-what table (shared/who-approves-what.md)

Fill in one row for each task in the ship item. The "Approves" column is always a named person.

TaskReversible if wrong?TierWho does itApprovesAccountableWho needs to know
example: write a draftyes1makermememanager
example: send the draft to a colleagueno2mememecolleague
example: change a shared system configurationno3person with authoritymanagermanagerteam

Three tiers, matching the Week 4 material:

  • Tier 1, the agent runs on its own. Only for reversible tasks. You do not approve the result before it is used; you only check the input of the task before it runs (step 4 of section 7) and check the result afterwards, through the verdict.
  • Tier 2, you approve by hand. An irreversible task that is within your authority. You do it by hand after the verdict passes.
  • Tier 3, someone with higher authority approves. An irreversible task that is outside your authority.

Rules of the table:

  • The "Who does it" column is an agent only when the tier is 1.
  • Irreversible tasks include: sending a message to a person, posting, deleting, spending money, sending data out of the tool, changing a shared system, merging or releasing.
  • If you are not sure whether a task is reversible, write "not sure" and treat it as "no".
  • An agent is never in the Approves or Accountable column.
  • If the coordinator writes "not linked yet" for a task, you add a row for that task to the table first, then continue the run.

6. The real agent running cost table (cost-log.md)

Write one row per run. A cell the tool does not report gets "not reported", do not estimate to make it look good.

RunRoleTool and model name (as the screen shows it)Machine run minutesTokens in / outMoney (unit, or "flat plan")My human minutes (reading, passing files, checking)Result of the run

At the end of the week work out three numbers, writing "not measured" if data is missing:

  1. Your total human minutes divided by the number of tasks graded PASS.
  2. Total money (or tokens) divided by the number of tasks graded PASS.
  3. The agent running cost per unit: the week's total human minutes and total money (or tokens), divided by the number of units finished in the week. The unit is the unit you chose in Week 2 (for example one release, one ticket, one report). A week in which no unit is finished gets "not measured".

A task counts as one task line with a PASS verdict. The first two numbers are for you to run the agent team; the third number is the one you carry to the re-measure session.

7. Steps to run one full run

  1. Create the folder of section 1. Copy the ontology, the spec and the working rules into shared/. Fill in the table of section 4 for the whole ship item. Put the materials of this run into inputs/.
  2. Edit the three role files of section 2 (replace the <...> parts).
  3. Open session A. Paste coordinator.md, the NNN-task.md format block from section 3, the files in shared/, and the materials of this run. If one material is used only by the runner (section 2), do not paste it: add one line that names the file and says what it is. Request: "Pick one Tier 1 task and write 001-task.md." Save to file.
  4. You read 001-task.md and check four things: the task matches one Tier 1 row in the table; the materials are something you are allowed to put into an AI tool; the criteria are copied word for word; and a maker who knows nothing can do the task from this file alone (a task that fixes or continues an existing product has that product word for word in the Materials section; the task does not ask the maker to run commands). If all four are right, you fill in your name and the time on the two approval lines. For a Tier 1 task, this signature only means "the input was checked before the run"; it does not approve the result, and it does not turn a Tier 2 or Tier 3 task into a task the agent may do. If something is wrong, tell the coordinator to write it again.
  5. Open session B. Paste maker.md, ontology.md, the skill if there is one, and 001-task.md. Save to file 001-result.md. If the last line is not DONE or DONE_WITH_CONCERNS, stop and read the reason.
  6. If the product must be run to know whether it is right (code, script, formula, configuration): you put the product in a place to test it, run it yourself, then add to the end of 001-result.md the section Human-run evidence with the command and the real result. Run exactly the product in the result, change no word, and write that sentence in this section: the grader cannot check this itself, so your word is all it has for it. If the product does not run, do not fix it for the maker; write the exact error in this section. Materials only the runner uses (for example a large data file) you prepare yourself and use at this step. If you have nowhere to run the product, write "could not run" in this section: the criteria that need a run stay NOT_VERIFIED, and the ship item is recorded as "not done, criterion N not measured", not as done. If the product is only text, skip this step.
  7. Open session C, a completely new session. Paste grader.md, spec.md, ontology.md, 001-task.md, 001-result.md. Paste nothing from session B except the result file. Save to file 001-verdict.md.
  8. You read the verdict. For each PASS line, open the product and see the evidence yourself. Write the human minutes into the cost-log.
  9. If there is a FAIL line: go back to old session B, paste only the verdict file, save to file 001-result-r2.md. If the product must be run to know whether it is right, redo step 6 for the new version. Open a new grading session following step 7, save to file 001-verdict-r2.md. At most three runs for the same task, each time fixing at the root and not patching only the spot the verdict just pointed at; after the third, stop and ask for more information from the person who has it, do not try to guess a fourth time. (The owner's rule used: when a gate fails, try at most three times, each time fixing at the root, then stop and ask for input; the owner’s OPC article, section Principles.)
  10. If there is a NOT_VERIFIED line: this is your job, not the agent's. Find what is missing (ask the person with the information, measure, run a command), write it into the materials or into the human-run evidence section, then grade again with a new session. Two grading sessions can differ exactly on these criteria: in the dry run, with the same evidence, one session graded PASS and two sessions graded NOT_VERIFIED. When in doubt, run a second grading session; if they differ, you decide and write the reason in the verdict. In the dry run of 2026-11-13 with code, once there was human-run evidence, the two grading sessions gave the same word on every criterion that belonged to the task. If a criterion stays NOT_VERIFIED because one of its words can be read in two ways (in the run with the English role files, "the maker's machine", when the maker is an agent that has no machine), adding a sentence to the evidence does not settle it: a new grading session gave NOT_VERIFIED again. Change the wording of the criterion in spec.md, write the date and the reason there, have the coordinator write the task again in old session A, then grade again with a new session.
  11. The VERDICT is PASS: for each related Tier 2 or Tier 3 task, you or the approver do it by hand. The agent does not.
  12. If a criterion in spec.md still has no PASS line: go back to old session A. Copy the Product section of the PASS result on its own into a file in inputs/, then paste the verdict file and that file (the coordinator does not read the result file). Request: "Write the next task." The task number goes up: 002-task.md. Check it following step 4. The maker of the new task is a new session B, because it needs only the task file. For the new task, redo steps 4 to 11, replacing 001 with the number of that task, then come back to this step 12. Stop when every criterion has a PASS line on the final version of the product, or when the remaining criteria are ones you cannot measure (write "not measured" as in step 6).
  13. Complete cost-log.md and schedule.md for this run.

8. The planted-defect test (for the peer-grading session and for yourself)

Purpose: to prove the grader knows how to report FAIL.

  1. The peer grader chooses exactly one criterion in spec.md, excluding any criterion that the verdict of that run marks NOT_APPLICABLE (the Given part does not occur with the materials, or the criterion does not belong to the task of the run).
  2. You copy the NNN-result.md of a run that already has a verdict to NNN-result-broken.md and change it to violate exactly that criterion, changing as few lines as possible. If the product must be run to know whether it is right, change the product itself (for example one line of code), delete the old Human-run evidence section, then redo step 6 of section 7 for the changed version. The name of the test place and every word in the new evidence section must not contain the word "broken".
  3. Open a new session, paste for the grader again following step 7 of section 7, with the changed result. The file-name line you write when pasting is NNN-result.md, without the word "broken": the grader must not know this is a planted-defect version. Save to file NNN-verdict-broken.md. These two files never replace the real result and verdict of the run.
  4. It passes when the grader's verdict says FAIL on exactly that criterion, with the violating line quoted, and the table of section 4 has no Tier 2 or Tier 3 task whose "Who does it" column is an agent.
  5. If the grader reports PASS despite the violation: edit the file grader.md (add a specific check for that criterion), do not change the criterion to make it easier to pass. Run again from step 3 of this section.
